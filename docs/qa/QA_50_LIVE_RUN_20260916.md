## Bugs (grouped by category, most severe first)

### 1. [CRITICAL — code/routing] "Entity Memory" false-positive hijacks fresh, fact-rich legal questions
- **File:** `app/memory/entity_memory.py`, `is_recall_query()` (~line 249) and `matches_known_category()` (~line 306).
- **Reproduced independently 5 times:** Q02, Q25, Q32, Q36, Q46 — different sessions, different identities, different topics (theft / tenancy / loan / fabricated-Act probe).
- **Root cause:**
  - `is_recall_query()` treats *any* interrogative word (`kya`/`kaun`/`kisne`/`what`/`who`) as recall intent unless blocked by `_ACTION_SEEKING_PATTERN` or `_DEFINITIONAL_PATTERN`. The action-seeking allow-list's `kya\s+(karu|kru|karoon|kare|karna|krna)` alternation is **missing "karun"** — a very common spelling of "what should I do" — so "Main kya **karun**?" (Q25) is not recognised as action-seeking.
  - `matches_known_category()`'s entity-only fallback fires on **any** message containing a first-person possessive (`mera`/`meri`/`mere`/`my`) plus **any** of ~40 generic nouns (bike, phone, house, landlord, neighbour, deposit, money, notice, agreement, police, court…) — a combination that is close to the *default* shape of an ordinary Hindi/Hinglish personal legal question.
  - When both fire and nothing is yet stored for that exact category+entity (always true on turn 1), the code emits the hardcoded `format_no_memory_answer()` string instead of routing to the real legal/drafting logic — silently discarding the entire user message.
- **Reproducible input:** `"Meri bike kal chori ho gayi. BNS mein theft ki definition aur punishment kya hai, aur complaint dene ke liye kya details taiyar rakhun?"` (Q02) on a fresh, unauthenticated session with no prior turns.
- **Impact:** broke the very first turn of the flagship memory-chain scenario, the chain's own recall checkpoint, a fresh M2 identity's first turn, and a safety-adjacent fabricated-citation probe. Confidence is reported as `1.0 High` on every one of these wrong answers — also a confidence-calibration defect.

### 2. [CRITICAL — code/state machine] Session gets stuck in a `document_timeline`/`case_list` workflow
- **Reproduced in:** M1 turns Q28, Q29, Q30, Q33, Q34, Q38 (6 of 10 M1 turns after entry point), plus independently Q41 and Q50.
- Once triggered (apparently by a "draft banao" instruction following a message that mentioned "bill"/"agreement clause" — Q27→Q28), **every subsequent turn in that exact `session_id`** returns a near-identical canned English sentence ("Attach the document here and I will read it." / "You have no case files yet…") **regardless of the requested output language** (Q29 asked Marathi, Q30 asked English explicitly — same sentence both times) **or content** (Q33 asked for arithmetic, Q34 asked for a summary).
- The state is sticky in the persisted session, not per-request: a topic detour (Q31) temporarily escaped it, but the very next on-topic turn (Q33) snapped back into it.
- **Consequence:** this single bug is responsible for the failure of the two turns most central to the memory-chain test design — the mandated 5-point summary (Q34) and the mandated post-detour recall (Q38) — even though the underlying stored memory was, by then, accurate (see the persistence-check note under Q25–Q34 above).

### 3. [HIGH — retrieval/multilingual] Zero-retrieval KB fallback for 10 of 24 languages regardless of topic
- **Languages:** Assamese, Kannada, Kashmiri, Konkani, Maithili, Malayalam, Manipuri, Nepali, Sanskrit, Santali — 10/24 (41.7%) of the auto-detect language batch, across 10 unrelated topics (RTI, FIR-refusal, police notice, FIR-vs-complaint, unpaid salary, unauthorized bank transaction, photo-threat, contract basics, legal-notice-definition, consumer evidence).
- Kannada in particular is a large, well-resourced language, and Q39/Q40/Q45/Q47 (English/Hinglish, not even a script issue) hit the identical fallback for foundational topics (HMA divorce grounds, CrPC↔BNSS maintenance, legal-notice process, culpable homicide/murder) that plainly exist in the KB in some form (BNS/BNSS chunks were retrieved successfully elsewhere in this same run). This suggests a retrieval/embedding-coverage gap broader than just "content isn't in the KB."

## Supplementary finding — manual UI test, not part of the mandated 50

Found by the user during separate manual testing of the document-upload/OCR flow via the app UI
(Streamlit console), not part of the automated 50-question batch above. Recorded here because it's
the same class of defect as several findings above (a message outside the app's fixed recognized-
command set gets silently detached from the active document/session context and answered from
unrelated general retrieval instead).

**Setup:** uploaded a screenshot of a printed Hindi legal document — a "Contempt of Court"
application template (addressed to a Magistrate/SP, alleging non-compliance with a court order and
threats, with placeholders for case number, order date, and the opposing party's required action).
Ground-truth OCR text is preserved at
`legal_ai_assistant/output/handwriting-smoke/user-screenshots/Screenshot 2026-09-16 134403.txt`.

**What worked correctly:**
- Initial upload → correct summary ("template for an application regarding violation of a court
  order (Contempt of Court), requesting police assistance...") and correctly flagged 3 missing
  fields (applicant name/address, opposing party name/address, case number).
- `"show the risky clauses"` → correctly identified "Non-compliance and Threat — high risk (page 1)"
  with sensible, appropriately hedged follow-on risk notes ("these are points to raise, not legal
  conclusions").

**What failed:**
- `"isme se text extract kr lo"` ("extract the text from this") → the app returned a summary of
  **Article 165 of the Constitution (Advocate-General for the State)** — entirely unrelated content
  that has nothing to do with the uploaded Contempt-of-Court document. The actual document text
  (verified against the ground-truth OCR file above) was never returned.

**Likely cause:** the UI's own suggested follow-ups for an attached document are a fixed set —
`"summarise it"`, `"review it against a checklist"`, `"compare it with another"`,
`"ask a question about it"` — and plain-language phrasing outside that set (here, an explicit
"extract the text" request) isn't recognized as a document-bound follow-up. The message appears to
have fallen through to general legal-knowledge-base retrieval instead, which then answered from
whatever unrelated chunk it matched, while silently dropping the already-active document context.
This mirrors BUG-2 and the Q41 misroute above: the app's document/session context only survives a
narrow, fixed set of recognized phrasings, not free-form requests that mean the same thing.

**Severity:** HIGH — a user asking their own attached document to be read back to them (a basic,
expected capability directly relevant to a low-literacy or OCR-uncertain use case, which is exactly
what "handwriting-smoke" testing is for) instead silently receives unrelated constitutional-law
content with no indication anything went wrong.

**Status: FIXED and live-verified (2026-09-16, same day).** Root cause was exactly the hypothesis
above: neither phrasing matched any registered `chatops` workflow's intent pattern, so both fell
through to general retrieval with the document silently dropped from context.

**Fix:** added a new `DocumentTranscribeWorkflow` (`app/chatops/workflows/documents.py`) plus a new
`DOCUMENT_FORMAT` intent pattern (`app/chatops/intents.py`) recognizing this request shape across

format this document," a typed/clean/professional + write-verb combination, etc.), guarded so it
never steals a genuine "draft a brand-new document" request. Execution calls a new
`document_insight.transcribe_document()` (new prompt: `document_transcribe_prompt.md`; new schema:
`app/schemas/document_transcribe.py`), which retypes the document's own already-OCR'd text into a
clean, professionally formatted version while enforcing: no invented facts/names/dates, original
language/script preserved, blank fields kept blank, `[UNCLEAR]` for unreadable text,
`[Signature]`/`[Official Stamp/Seal]` placeholders, and a `verification_required` flag with reasons

scanner the way `DocumentService.analyze()` does (see BUG-7 above) — a scanned legal document

### Follow-up fix, same day: Streamlit rendered the retyped document as one unbroken paragraph

Live-tested by the user on their own upload/session, via the actual Streamlit UI. The generated
`formatted_text` was factually correct, but the address block (heading/"To"/officer/district lines)
and the numbered annexure list rendered as one squashed blob of text on screen instead of the
document's real line-by-line layout.

**Cause:** the chat answer is rendered as Markdown, and Markdown collapses a single `\n` into
nothing (only a blank line, `\n\n`, starts a new visual line/paragraph). The prompt asked for the
document's "original structure" but did not say *how* to encode line breaks so they would survive
Markdown rendering, so the model used single newlines between lines that were single newlines in
the source, e.g. the three-line address block and the annexure list — which is faithful to the
source's raw structure but invisible once rendered.

**Fix:** `document_transcribe_prompt.md` now explicitly tells the model that `formatted_text` is
rendered as Markdown, that a single `\n` is collapsed, and that **every** visually distinct source
line (heading, each address line, subject, salutation, each body paragraph, the annexure heading,
each numbered annexure item, and the closing date/signature line) must be separated by a full blank
line (`\n\n`), never a single newline. Backend restarted to clear the prompt-file cache (`lru_cache`
in `app/llm/prompts.py` keys on file content read at process start, so a `.md`-only edit is not
picked up by `--reload`, which by default only watches `.py` files, without a process restart).

**Verified live** (fresh upload, same ground-truth document, same `"isko likh ke de do proper"`
phrasing): the raw JSON answer now shows `\n\n` between every one of the heading/address/subject/
salutation/body/annexure-item/date/signature lines, confirmed via `repr()` on the raw response
before rendering — this will display with the document's real line-by-line layout in Streamlit (or
any other Markdown renderer) instead of one run-on paragraph. Regression suite re-run, still 257
passing (prompt-text-only change, no Python logic touched).
