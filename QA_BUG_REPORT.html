3 bugs

Found and fixed before the QA pass, while building the state-adapter/bulk-review tooling. Re-verified live by Agent 4 (KB admin pass) after the fix — confirmed holding, including through real chat retrieval.

F1
Review queue showed 2,174 documents waiting when only 21 actually were
Fixed

The Streamlit review page read a staging-ledger snapshot of review_status taken once at indexing time — it never updated after a document was later approved. The count only ever grew.

Fix: new endpoint GET /admin/knowledge-base/documents/needs-review queries live status directly from uploaded_documents.

app/services/kb_ingestion_service.py, streamlit_app/legal_source_review_page.py

F2
"Strong evidence" signal never lit up for any document, ever
Fixed

The review page's "all green / quick verify" check ran on a payload that had already had machine_verification stripped out of it (deliberately, so stale evidence isn't resubmitted) — so the evidence check was structurally unreachable, for every document, always.

Fix: _signals_for_record() re-injects the raw, never-resubmitted evidence just for the check.

streamlit_app/legal_source_review_page.py

F3
Clicking "Publish" silently downgraded verified → inferred — document never actually became retrievable
Fixed

An automation-discovered document's existing metadata_provenance: "automated_official" tag leaked into the resubmitted payload. normalize_jurisdiction reads that field from the submission in preference to the endpoint's own provenance=MANUAL default — so a non-manual provenance silently downgrades verified to inferred. The UI reported 200 OK; the document never actually reached shared retrieval, no matter how many times it was republished.

Fix: strip metadata_provenance before resubmission, in both the Streamlit form and the new bulk-review backend method.

app/services/kb_ingestion_service.py, streamlit_app/legal_source_review_page.py

Chat, voice, search, history, auth

10 bugs

Core conversational surface. 4 of the 6 open critical bugs in this whole report are here.

C1
Any account (or no account at all) can read and overwrite another user's session facts, before that session's first chat message
Critical

Cause: a session's owner_user_id is only bound the first time POST /chat is called for that session_id. Before that, GET/PATCH/DELETE /session/facts, PUT /session/missing-details and GET /session perform no ownership check.

PATCH /session/facts?session_id=X (User1 token) → sets secret_key GET /session/facts?session_id=X (User2 token, or NO token at all) → 200, returns User1's data PATCH /session/facts?session_id=X (User2 token) → 200, overwrites it

Once /chat is later called on that session, ownership retroactively binds and 403s correctly kick in from then on — but by then the tampered data is already saved.

Impact
Cross-account read + write, zero auth boundary, in a real pre-launch window.
File
app/api/chat.py or app/services/session_facts (session ownership binding)
C2
"Delete all my data" reports success but leaves chat history completely intact
Critical
DELETE /me/data → 200 {"status":"deleted","deleted":{"chat_messages":0, ...all zero...}} GET /history?session_id=X → full question+answer history, still there, untouched

Contrast test: DELETE /session?session_id=X on the exact same data correctly reports chat_messages:1 and actually empties it — proving deletion itself works, the account-level endpoint's targeting/counting logic is simply wrong.

Impact
This is the privacy/GDPR-style "erase my data" feature. It doesn't erase chat history, and the 200 response actively tells the user it did.
C3
Model's internal reasoning / system-prompt text leaks verbatim into a user-facing answer
Critical

100% reproducible, 2/2 tries, with a specific two-turn sequence (ask a substantive question, then "Is it a cognizable offence?" as a follow-up on the same session). The answer field contains a literal </think> tag and lines like "The instructions say: ... The system prompt says: 'if it's empty or actually about something else, output Rule 2's exact fallback line...'" — before finally emitting the intended fallback.

Also returns a broken non-answer instead of the real one (the question was in fact answerable from context the model had).

Impact
Discloses internal prompt content; user sees a garbled, unprofessional response instead of an answer.
C4
The same document exists as two Mongo records with contradictory review status — the admin queue shows a stale duplicate while a different duplicate is what's actually served live
Critical

Two filenames (a Lalita Kumari judgment PDF, a Delhi Police FAQ PDF) each have two document records with the identical document_hash and version_number — one flagged needs_review/unverified, the other approved/verified and the one chat actually cites.

An admin reviewing the needs-review queue is looking at content that's already superseded by an already-approved twin — false confidence about what end users see, and wasted review effort.

C5
explanation_mode request field has zero effect
Major

simple / detailed / advocate all returned byte-identical answers on the same question; explanation_level in the response stayed "citizen" in every case. Accepted (no 422), silently a no-op.

C6
A question about one Act gets silently answered from a different Act, with no note
Major

"What is Section 302 of the Bharatiya Nyaya Sanhita about?" (the penal code) was answered entirely from Section 302 of the Bharatiya Nagarik Suraksha Sanhita (criminal procedure) — a different Act — with no disclosure that the named Act had no matching content or that the answer came from elsewhere. Likely to mislead, since IPC §302 (a number many users already know) means murder; the actual answer is an unrelated procedural provision.

C7
DELETE /chat reports the wrong count of messages deleted
Minor

Reports messages_deleted: 1 when 2 messages (user + assistant) were present and both were actually removed. Deletion itself is correct — only the number is wrong.

C8
Chunk language metadata is unreliable
Minor

The (English) Bharatiya Nyaya Sanhita 2023 PDF is tagged "language": "hindi" across multiple cited chunks. Any feature that trusts this field (language filters, UI labels) would misbehave.

C9
Voice transcription hallucinates text from silence
Minor

A fully silent 1-second WAV produced a transcribed "So my mom" instead of recognizing no speech. Likely inherent STT behavior needing a VAD/silence gate rather than an app-logic bug.

C10
POST /search works with no Authorization header
Minor

Returns real 200 results fully unauthenticated. Possibly intentional as a public endpoint — flagged to confirm that's the intent, since every sibling endpoint requires auth.

Document drafting

3 bugs

38 endpoints — the AI-assisted legal document generation and export pipeline.

D1
When the LLM times out, the fallback document silently drops rent, deposit and other collected figures — across all 8 contract templates
Critical

When the LLM call exceeds its timeout (observed at >88s), the engine falls back to a "deterministic" generator. For every template in the Contract family (rent, NDA, MOU, partnership, service, property purchase/sale, business proposal), that fallback only ever reads a fixed handful of fields (purpose, term, parties, governing law) — it never reads template-specific fields like monthly rent or security deposit.

The draft still reaches preview_ready, is fully exportable, and can be approved/locked/exported with the money terms permanently missing from the actual document text — while GET /draft/{id}/review shows them correctly stored in user_facts the whole time. The data isn't lost; the renderer just never looks at it.

Confirmed systemic by reading _deterministic_contract_sections (app/drafting/engine.py:2672), not a one-off.

File
app/drafting/engine.py, _deterministic_contract_sections / _deterministic_sections
D2
Exported PDFs of Hindi content look correct on screen but extract as garbled text
Major

A Hindi-translated draft, exported to PDF: visually renders crisp, correctly-shaped Devanagari (confirmed by rendering to PNG) — but text extraction (PyMuPDF and pypdf, cross-checked) is corrupted: "किराया अनुबंध" extracts as "Įकिराया अनुबंध", with a spurious Į (a character with no place in Hindi text) and scrambled vowel-sign ordering. English-only exports of the same draft extracted cleanly — this is specific to complex-script shaping in the PDF's ToUnicode mapping.

Looks fine to a human printing or reading it; breaks copy-paste, in-PDF search, accessibility, and any automated text extraction downstream (e-filing portals, audit tooling).

File
app/drafting/export.py, PDF generation path (WeasyPrint)
D3
Hallucination audit fires false positives on ordinary statute years, drowning out real findings
Moderate

POST /draft/audit on a normal, correctly-generated draft returned ok: false with 6 findings — all flagging standard Act years (1882, 1908, 2021) and the document's own auto-filled signing date (2026) as "unsupported figures," none of which were ever meant to come from user facts.

This will train reviewers to dismiss audit_findings as noise — meaning a genuine hallucinated figure (a wrong rent amount the LLM invented) would be buried among routine false alarms instead of standing out.

Cases & notarization

7 bugs

39 endpoints. The core "get notarized, then verify" journey could not be exercised at all — flagged separately below.

N1
The e-sign callback token is generated, then discarded — no legitimate caller can ever complete a signing callback
Major

initiate_signing() computes a callback_token but never puts it in the API response and never attaches it to the outgoing provider request (callback_url defaults to empty). POST /notarization/signing/callback requires exactly that token — which now exists nowhere a real client or provider could ever obtain it.

Architectural, not config-specific: this would block a real e-signing vendor integration too, not just this deployment's "manual" provider.

File
app/notarization/service.py:339, app/api/notarization.py:183
N2
Full notarize → verify pipeline is unreachable in this deployment — could not be tested end-to-end
Major

Only provider configured is manual, whose initiate() always returns pending and never transitions a document past ready_for_signature — so signed, and therefore notarized, is never reachable through the live API. Confirmed the state-machine guard itself is sound (a self-signed grey-box token was correctly refused for an invalid transition), but the actual notarize-then-verify-then-QR user journey — the thing this pass most needed to confirm — was not exercisable at all.

Recommend: a test/mock provider that actually reaches signed, or an admin "record external signature" escape hatch, before launch.

N3
GET /notarization/eligibility has no authentication
Moderate

Unlike every sibling endpoint, this one is reachable with zero Authorization header and returns another user's draft category/eligibility. Content isn't exposed, but it's an inconsistent trust boundary in an otherwise carefully-gated module.

File
app/api/notarization.py:152
N4
A case can link to any document/draft ID string — no existence or ownership check
Moderate

attach_document/link_draft just append whatever ID string is supplied; a bogus ID surfaces straight into lawyer-summary. No check that it exists, and no check that the caller owns it — worth closing before anything dereferences these arrays to fetch real content.

File
app/services/case_service.py:159-174
N5
resolve_case_conflict accepts any slot name, not just real pending conflicts
Minor

No check against case.unresolved_conflicts. Low impact — only pollutes the owner's own data — but same "unchecked input" pattern as N4.

N6
Two different rate-limit error response shapes
Minor

The notarization-specific limiter returns the app's standard {"error":{"code","message"}} envelope; the global rate-limit middleware returns FastAPI's default {"detail": "..."}. A client that only parses error.message mishandles the second form.

N7
Client can set its own task_id and create a task as already completed
Minor

Not a security issue on the owner's own case, but if task_id is assumed server-generated elsewhere, this could collide with or break that assumption.

Legal-source governance & automation admin

6 bugs

56 endpoints — source verify/review/supersede tracking, dashboards, evaluation runs, law-monitor and KB-automation job controls.

G1
Verifying a legal source updates the registry and audit log — but never reaches the actual document content users see
Critical

link_document() is the only code path that ever writes governance fields into a document's chunks, and it's a one-time snapshot copy at link time. review()/verify()/supersede() only update the separate legal_sources registry — none of them re-propagate into the chunks already linked to that source.

1. link-document → chunk metadata.verification_status = "unverified" (correct at this point) 2. POST .../review {"verification_status":"verified", evidence_url, review_notes} → 200, legal_sources record now correctly says "verified" 3. Re-check the SAME document's live chunks → still "unverified" — never updated, and stays that way through every future verify/supersede/rejection on that source, unless link-document is manually re-run

Same "signal never lights up" shape as F2 above, triggered a different way — a write succeeds in one place and is trusted to have propagated, but never does.

File
app/services/phase3.py, LegalUpdateService.review/verify/supersede
G2
POST .../legal-sources/{id}/verify can never actually set "verified" — the request schema is missing required fields
Major

VerifySourceRequest has no evidence_url/review_notes fields; the service wraps them with getattr(..., ""), which is always empty — and the underlying review logic unconditionally rejects "verified" without non-empty evidence. 100% reproducible, every source, every attempt.

POST /admin/phase3/legal-sources/{id}/verify {"verification_status":"verified","last_verified_date":"..."} → 400 "Verification requires an evidence URL..." (no request body can ever satisfy this endpoint)

Only the newer /review endpoint (which does declare those fields) can actually verify a source.

G3
Re-reviewing a source with a non-"verified" decision silently erases its recorded evidence; the "stale" flag ignores verification status entirely
Major

evidence_url/review_notes are unconditionally overwritten with whatever the new request supplies (default empty) — unlike every other field on this model, which only patches what's actually sent. Moving a verified source to pending_review with no evidence in the request wipes the prior verification's evidence trail, unrecoverable via the API.

Separately: the dashboard's stale flag is computed only from last_verified_date age and repealed/superseded status — not from verification_status. A source can move from "verified" down to "pending_review" or even "rejected" and register as stale: false as long as the date is fresh, which undermines exactly the signal the governance dashboard exists to surface.

G4
Law-monitor "check" gives the same response for a busy monitor and a nonexistent one
Minor

POST .../law-monitors/{id}/check on a mistyped/deleted ID returns 200 {"status":"busy"} instead of 404 — an admin will wait for a lease that will never clear.

G5
Retrying a nonexistent automation job "succeeds" silently
Minor

POST .../kb-automation/jobs/{id}/retry on a bad ID returns 200 {"requeued": false} — same shape as "exists but wasn't failed." A typo'd ID gives no error signal.

G6
No way to fetch a past evaluation run's results except the single most recent one
Minor

Runs persist to Mongo with a real run_id, but no GET /evaluations or /evaluations/{run_id} exists — running a second evaluation makes the first permanently unfetchable through the API, even though it's sitting in the database.
