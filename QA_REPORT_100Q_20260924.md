Of the 100 tests, **zero answers were flagged as affirmatively legally wrong** (no test produced a confident, specific, incorrect statement of law that was checked and found factually false). One draft (Cheque Bounce Notice under NI Act §138) was carried through the full lifecycle: trigger → field collection → correction → regeneration → version history → PDF export → DOCX export → Hindi→Tamil translation → concurrent-edit safety. ## 1. Critical bugs

### BUG-101 — System collapses under light concurrency; local vector search is O(n) per query and doesn't scale
**Severity:** Critical | **Area:** Performance / Concurrency | **Evidence:** `qa-100q-full-20260924/CONCURRENCY_BUG_EVIDENCE_6way.log` (64 lines), `backend_bug07_verify_20260924.log`

**What happened:** Firing 6 concurrent `/chat` calls (a modest, realistic load — 6 users asking a question at the same moment) caused:
```
{"scan_limit": 20000, "hint": "Raise LOCAL_VECTOR_SCAN_LIMIT or configure Atlas vector search.", "event": "local_vector_scan_hit_cap"}
{"candidate_count": 20000, "mongo_scan_ms": 106778.25, "score_ms": 93274.07, "event": "local_vector_timing"}
{"embedding_retrieval_ms": 197328.57, "bm25_candidate_count": 0, "event": "hybrid_retrieval_timing"}
{"error": "Timeout reading from localhost:6379", "event": "bm25_retrieval_failed"}
{"error": "invalid input for query argument $4: '2026-09-24T06:30:16...' (expected a datetime.date or datetime.datetime instance, got 'str')", "event": "long_term_memory_write_failed"}
{"chunk_count": 54007, "persist_ms": 89796.48, "event": "bm25_update_timing"}
```
- Local (non-Atlas) vector search does a **brute-force linear scan of up to 20,000 candidate chunks per query**, scoring cosine similarity for all of them. Under concurrency this took **93–107 seconds just for the Mongo scan+score step**, and **194–197 seconds for embedding retrieval end-to-end** — all 6 concurrent test requests exceeded a 180-second client timeout and never completed.
- The BM25/Redis leg of hybrid retrieval timed out entirely under the same load, silently returning 0 candidates.
- A Postgres write (`long_term_memory_write_failed`) failed on every single one of the 6 concurrent requests with a type error (a string passed where asyncpg expects a native `datetime`) — this one degrades gracefully (logged as a warning, doesn't crash the request) but is itself a real, distinct bug (a `datetime` is being serialized to its ISO string somewhere upstream of this specific write call and never converted back, the same class of issue as BUG-102).
- Persisting the updated BM25 index took **89.8 seconds**.
- When the test client was killed mid-run (forced by this stall) and the backend restarted, the on-disk BM25 index was found corrupted (`"Ran out of input"`) — the system self-healed via a full rebuild, but this shows a hard-kill during a slow persist can corrupt index state (see BUG-113).

**Root cause:** README itself documents this limitation — *"Use MongoDB Atlas Vector Search in production by replacing the local cosine fallback in `MongoVectorStore.search`"* — but the deployed/tested configuration is running the local, non-Atlas fallback, which does not scale past trivial concurrency.

**Why Critical:** This isn't a rare edge case — 6 simultaneous users is a low bar for "production." At this load the app effectively stops responding (multi-minute latencies, silent BM25 failures, failed writes) rather than degrading proportionally.

**Recommendation:** Do not go to production on the local vector fallback. Configure MongoDB Atlas Vector Search (already anticipated by the codebase) or an equivalent ANN index before any concurrent-user load test is attempted again.

### BUG-102 — `GET /draft/{id}/versions` crashes 500 (same bug class as the already-fixed BUG-02, different call site)
**Severity:** Critical | **Area:** Drafting / Version history — explicitly named in the QA scope

**Evidence:** Live call against a real, completed draft (`draft_id=839d9cb0-0f62-49af-8a29-e08271ac810a`) returned:
```json
{"error": {"code": "internal_error", "message": "An unexpected error occurred.", "details": {}}}
```
Server traceback:
```
File "app/api/drafting.py", line 683, in list_draft_versions
    created_at=version["created_at"].isoformat() if version.get("created_at") else None,
AttributeError: 'str' object has no attribute 'isoformat'. Did you mean: 'format'?
```

**Root cause:** Identical pattern to the previous session's BUG-02 (`app/drafting/engine.py:839`, already fixed): with `POSTGRESQL_ENABLED=true` (the default), a `created_at` value round-tripped through the JSONB `payload` column (`app/repositories/postgres_json.py::dump_payload`/`load_payload`) comes back as a plain ISO **string**, not a `datetime`, because `dump_payload` serializes datetimes to strings on write and `load_payload` never converts them back on read. The previous fix only patched the one call site it was investigating (`engine.py::history()`); this is a **second, independent call site** with the exact same bug, confirming the underlying pattern is systemic wherever `version["created_at"].isoformat()`-shaped code touches a Postgres-JSONB-stored draft or draft-version record, not a one-off.

**Impact:** `GET /draft/{id}/versions` — the version-history feature, explicitly in scope for this QA pass — is completely non-functional for every draft, every time, under the current default configuration.

**Recommendation:** Same fix pattern as BUG-02 (`isinstance(value, str)` guard, or parse-then-reformat), applied here; and — more importantly — a codebase-wide `grep -rn '\.isoformat()' app/` audit to find every other place this exact pattern could recur, since this is now the second instance found by testing rather than by code review.

### BUG-103 — Drafting-intent trigger detection fails for the large majority of languages/phrasings, including bare configured trigger phrases
**Severity:** Critical | **Area:** Drafting engine — this is the app's headline differentiator per its own README ("Drafting happens entirely inside the normal chat conversation... detects drafting intent automatically")

**Evidence:** 6 independent drafting-trigger attempts, each sent as a fresh message with no prior context:

| # | Language | Message sent | Result |
|---|---|---|---|
| T033 | English | *"I want to file a consumer complaint"* (an exact, literally-configured `trigger_phrase` in `consumer_complaint.yaml`) | **Failed** — classified as "General Legal Information" |
| T034 | Hindi | *"पुलिस शिकायत"* (the exact, literally-configured Hindi `trigger_phrase` in `police_complaint.yaml`) | **Failed** — classified as "General Legal Information" |
| T035 | Hinglish | *"cheque bounce ho gaya hai, notice draft karna hai"* | **Succeeded** — entered `collecting` stage correctly |
| T036 | Marathi | *"पोलीस तक्रार नोंदवायची आहे"* | **Failed** |
| T037 | Tamil | *"நுகர்வோர் புகார் பதிவு செய்ய வேண்டும்"* | **Failed** |
| T038 | Bengali | *"ভোক্তা অভিযোগ দায়ের করতে চাই"* | **Failed** |

**5 of 6 failed, including two that used the exact, literal, already-configured `trigger_phrases` from the template YAML files themselves.** This is a significant escalation from the previous session's finding (which showed narrative-wrapped triggers losing to the LLM intent classifier) — here even a *bare, unadorned, exact-match* trigger phrase in English and Hindi failed to invoke drafting.

**Root cause:** Not re-diagnosed at the code level this run (instruction was report-only), but consistent with the previously-identified pattern: the LLM-based conversational-intent classifier can override an exact keyword/trigger-phrase match rather than deferring to it.

**Why Critical (escalated from High last session):** This isn't a phrasing edge case anymore — it's the *majority* failure mode across a clean sample, in the app's core language (Hindi) and primary language (English), using the exact phrases the app's own templates say should work.

**Recommendation:** Treat an exact `trigger_phrases` match as authoritative (short-circuit or heavily bias the intent classifier) rather than advisory. This is the single highest-leverage drafting fix available — it doesn't require solving general multilingual intent classification, just making already-known-good literal matches reliable.

## 2. High-severity bugs

### BUG-104 — Field-collection NLU only matches a field's display *label*, not the field *key* the API itself reports as missing
**Severity:** High | **Area:** Drafting field extraction

**Evidence:** A cheque-bounce draft's `missing_fields` response listed `"dishonour_date"` (the internal YAML `key:`). Three separate attempts to fill it using that exact string — `"dishonour_date is 10-08-2026"`, then a broader summary re-statement, then a fresh-session retry — **all failed**, still reporting `dishonour_date` as missing. Rephrasing using the field's human-readable `label` instead — *"the date of return memo is 10 August 2026"* — **succeeded immediately**.

**Impact:** Any caller (human or API integrator) who reasonably tries to answer using the exact field name the API told them was missing gets stuck in a loop. This is worse than a cosmetic mismatch — it's actively misleading, since the API's own error-recovery hint (`missing_fields`) doesn't work as input.

**Recommendation:** Either have `missing_fields` return the human label (not the internal key), or make the extractor also match on the internal key, or both.

### BUG-105 — Drafting conversation state is lost by a generic, reasonable completion request mid-collection
**Severity:** High | **Area:** Drafting conversation engine

**Evidence:** Mid-field-collection, the message *"Please finalize the draft with the information already provided"* — an entirely reasonable thing for a user to say — caused the system to respond *"I could not find a saved draft to work with. Say 'show my drafts' to see what you have..."*, losing track of the in-progress draft entirely (`conversation_intent: "Workflow"`, no active draft state) rather than either continuing to ask for the missing field or recognizing the still-in-progress draft.

**Recommendation:** A completion/finalize-style utterance during an active `collecting`-stage draft should be handled by the drafting state machine itself (e.g., "here's what's still missing" or "generating now with defaults where reasonable"), not handed off to general intent classification.

### BUG-106 — Hindi-language (and several other Indian-language) RAG retrieval is unreliable even when the exact relevant content is indexed
**Severity:** High | **Area:** RAG retrieval quality — directly affects the two languages the QA brief names explicitly (Hindi, and Hindi-derived Hinglish edge cases)

**Evidence, four independent confirmations on the same well-indexed content:**
1. **T002** — Hindi phrasing of the NI Act §138 question → ungrounded GK fallback, while English (T001), Bengali (T004), Marathi (T013), Tamil (T021), Urdu (T023) and 6 other languages, asked the *identical* underlying question, all correctly grounded and cited §138.
2. **T026–T028** — a 3-turn Hindi conversation about a landlord not returning a security deposit → ungrounded GK fallback for all 3 turns, despite `Rent Control` (141 chunks), `Tenancy` (287 chunks), and `Transfer of Property Act` (515 chunks) all being confirmed present in the KB by direct MongoDB query.
3. **T025** — a romanized-Hindi (Hinglish) version of the same §138 question, with common typos → ungrounded, same pattern (compounds BUG-108, typo sensitivity).
4. **T072** — a direct `/search` call with a clean, well-formed English query (*"Section 138 cheque dishonour punishment Negotiable Instruments Act"*) → top results were **Maharashtra Court-Fees Act** and **CGST Act** (scores 0.049, 0.048), not the Negotiable Instruments Act, despite the correct content being directly confirmed present via MongoDB. **T074** similarly returned the wrong Act (Bharatiya Nagarik Suraksha Sanhita instead of the Bharatiya Sakshya Adhiniyam/Evidence Act asked about) with near-zero scores.

**Pattern:** this is broader than "Hindi is broken" — it's that retrieval relevance/ranking is inconsistent across the board, and Hindi-language and typo'd/informal queries are disproportionately affected. English queries mostly work (T001, T007 from the prior session, T047 keyword search) but not always (T072, T074).

**Why High, not Critical:** the failure mode is an honest "I don't have a verified source" rather than a wrong answer (the safety net from BUG-03's fix holds), so it's a completeness/quality problem, not a correctness/trust problem — but for an app whose stated audience is multilingual Indian users, failing on standard Hindi for a textbook legal question is a severe usability gap.

**Recommendation:** Investigate the embedding/reranking pipeline specifically for (a) Hindi Devanagari-script queries vs. the same concept in English/other-script languages, and (b) whether the local vector scan's `LOCAL_VECTOR_SCAN_LIMIT`/candidate-selection interacts badly with certain embeddings. Given BUG-101's finding that this is the same local (non-Atlas) vector path, a real ANN index may also improve relevance, not just latency.

### BUG-108 — Retrieval is not robust to typos, even minor ones, on otherwise well-indexed content
**Severity:** High | **Area:** RAG retrieval quality

**Evidence:** T024 (*"wat is teh punishment for chek bonuce in indai"*) and T025 (romanized-Hindi with similar typos) both fell back to ungrounded general knowledge for the **exact same NI Act §138 question** that T001 (correctly spelled) grounded perfectly. Real users make typos constantly, especially on mobile keyboards — this is not an edge case.

**Recommendation:** Add fuzzy/typo-tolerant query normalization before the embedding step, or verify the embedding model's own typo-robustness is being fully exploited (BGE-M3 should have some inherent tolerance; if it's not showing up here, the query pipeline may be doing something that defeats it, e.g. exact keyword pre-filtering upstream of semantic scoring).

### BUG-109 — Search mode `act` does not filter/boost by the named Act at all
**Severity:** High | **Area:** Search API

**Evidence:** `POST /search {"query": "Negotiable Instruments Act", "mode": "act"}` returned, as its top result, **"THE MAHARASHTRA MARITIME BOARD ACT"** (score 0.016) — completely unrelated to the query, despite the Negotiable Instruments Act being well-indexed and correctly retrievable via `mode=keyword` (T047, score 0.65) in the same test run. Search mode `section` (T050, bare query `"173"`) similarly returned an unrelated CGST Act match rather than anything BNSS-related.

**Recommendation:** `mode=act` should be filtering by/boosting the named Act via metadata (`act_name`), not running a generic semantic search on the Act's own name as free text (which produces near-random low-score noise, as seen here). Likely a missing filter-construction step for these two specialized modes.

## 3. Medium-severity bugs

### BUG-107 — Citation source labelling sometimes shows a missing or misattributed Act name
**Severity:** Medium | **Area:** Citation display quality (pre-existing, partially mitigated in code, still surfaces)

**Evidence:** T001's top-ranked source showed `act_name: None` for a Negotiable Instruments Act chunk, and a second source showed `act_name: "Repealing and Amending Act"` for what is actually a Negotiable Instruments Act §138 chunk (confirmed via `source_document`). The underlying `section` and `source_document` were correct in both cases — this is a display/labelling issue, not a grounding-accuracy issue (the code comments in `app/rag/citation.py` already acknowledge this exact failure mode and deliberately choose to drop a bad name rather than guess, which is the right call, but it still surfaces as a slightly confusing "None" or wrong-looking name to an end user).

**Recommendation:** Lower priority given the deliberate design trade-off already in place, but worth periodically re-running an act-name-extraction quality pass over the corpus to shrink how often "None" is shown.

### BUG-110 — Manipuri (and likely other very-low-resource-language) romanized input gets misclassified into a confusing non-answer
**Severity:** Medium | **Area:** Language detection

**Evidence:** T012 (romanized Manipuri: *"check bounce oirabadi India da kari punishment oi?"*) was detected as **English** and answered with *"I could not read 'kari' — did you mean 'kar', 'karo', 'karti'?"* — a Hindi-verb-conjugation spell-check prompt, nonsensical for the actual input language.

**Recommendation:** For languages marked `"experimental"` support, a clear "this language has limited support right now, please try Hindi/English/Hinglish" is much better UX than a confusing, wrong-language spell-check prompt.

### BUG-111 — Search modes `section` and `act` produce low-relevance noise on bare/short queries
**Severity:** Medium | **Area:** Search API (related to but distinct from BUG-109 — this is about query-design fragility generally, BUG-109 is specifically that `act` mode ignores the Act name)

**Evidence:** T050 (`mode=section, query="173"`) top result: CGST Act §173 (score 0.016) rather than BNSS §173 (the much more contextually likely intent, and confirmed present with a much higher score of 0.65 when queried via `mode=hybrid` with fuller context in T073).

**Recommendation:** Document that `section`/`act` modes need Act context in the query (not just a bare number/name) to be useful, or add that context automatically via `filters`.

### BUG-112 — Time-sensitive general-knowledge questions get a full refusal rather than the GK-fallback treatment
**Severity:** Medium (behavioral inconsistency, arguably defensible) | **Area:** Chat / GK fallback

**Evidence:** T031 (*"Who is the current Chief Justice of India as of this year?"*) returned a full `no_verified_context` refusal rather than an `general_knowledge_used` answer, unlike stable-fact GK questions (e.g. a capital-city question in the prior session's test suite) which do get answered via the GK-fallback path.

**Note:** this may be intentional and arguably *correct* conservative behavior — a "current" position-holder is exactly the kind of fact an LLM's training cutoff could get wrong — but it's inconsistent with the documented GK-fallback behavior and worth an explicit product decision either way rather than being an emergent side effect.

## 4. Low-severity bugs

### BUG-113 — A hard-killed backend during a slow BM25 persist can corrupt the on-disk index (self-healing)

Not data-lossy, but worth an ops-runbook note: don't hard-kill during heavy indexing.

### BUG-114 — Access-token TTL (~30 minutes) requires clients to implement transparent refresh, undocumented in this QA's discovery
**Severity:** Low (this is normal JWT design, not a defect — flagged for integration documentation) | **Evidence:** A token obtained early in this ~40-minute test run expired mid-flow (`exp` claim confirmed via decode), correctly rejected with 401, and the refresh-token flow (independently tested, T066) worked correctly to obtain a new one. Recommendation: ensure API/mobile-client documentation is explicit that `access_token` is short-lived and `refresh_token` must be used proactively, not just on first 401.

## 6. Root causes (grouped)

1. **Local (non-Atlas) vector search doesn't scale** (BUG-101): the single biggest root cause behind both the concurrency collapse and, likely, a meaningful share of the retrieval-quality inconsistency (BUG-106) — a brute-force 20,000-candidate scan is inherently both slow and a worse relevance signal than a real ANN index would give under resource pressure.
2. **The Postgres-JSONB `created_at` round-trip bug is systemic, not a single fixed line** (BUG-102): the previous session fixed one occurrence; this session found a second, independent occurrence in a different file. This strongly suggests more instances exist and haven't been exercised by either QA pass yet.
3. **The drafting engine trusts its LLM intent classifier over its own configured keyword triggers** (BUG-103, BUG-105): both failure modes (bare trigger phrase ignored; in-progress draft state dropped on a generic follow-up) trace back to the same design choice — free-text intent classification is given the final word even when a more deterministic, already-correct signal (an exact trigger-phrase match, or "there is an active draft in this session") is available.
4. **Field-extraction NLU and the API's own `missing_fields` output speak different vocabularies** (BUG-104): internal keys vs. display labels were never reconciled.
5. **No fuzzy/typo tolerance in the retrieval query path** (BUG-108), compounding items 1 and 3 above for real-world (imperfect) user input.

## 8. Reproduction steps (for the 3 Critical bugs)

**BUG-101:** With the backend running normally, fire 6+ concurrent `POST /chat` requests (any question that requires RAG retrieval) from 6 separate clients/threads. Observe response times exceeding 100s and backend logs showing `local_vector_scan_hit_cap`, `bm25_retrieval_failed` (Redis timeout), and `long_term_memory_write_failed`.

**BUG-102:** Complete any draft through to a `draft_id` (trigger → fill all required fields via chat), then `GET /draft/{draft_id}/versions?session_id=<sid>` with a valid Bearer token for the owning user. 500 every time, with `POSTGRESQL_ENABLED=true`.

**BUG-103:** `POST /chat {"question": "I want to file a consumer complaint"}` (or `{"question": "पुलिस शिकायत"}`) with no prior session context. Expect `draft.stage: "collecting"`; observe `draft: null`, `conversation_intent: "General Legal Information"` instead.
