## 1. Critical bugs (evidence-first, code NOT modified except Bug #1 by explicit user approval)

### BUG-01 — [FIXED, with approval] `torch`/`torchvision` version drift broke the entire RAG pipeline
**Severity:** Critical | **Area:** Chat, Search, Upload indexing, Drafting-via-chat

**Evidence:** Installed `torch==2.14.0` did not match `requirements.txt`'s pin (`torch==2.12.1+cu130`, matched to `torchvision==0.27.1+cu130`). Every embedding call crashed:
```
RuntimeError: operator torchvision::nms does not exist
...
ModuleNotFoundError: Could not import module 'PreTrainedModel'. Are this object's requirements defined correctly?
  File "app/rag/embeddings.py", line 110, in _get_model
    from sentence_transformers import SentenceTransformer
```
Full traceback saved at `qa-50q-full-20260924/prefix-bug-evidence/responses/T06_chat_hindi_bns_murder.json` (client-visible generic 500) and `legal_ai_assistant/backend_qa_50q_20260924.log` (server-side traceback). This affected **14 of 14** `/chat` calls and all `/search`, `/upload` calls in the pre-fix run.

**Notable:** `/health` reported `"embedding": "ok"` the entire time this was broken (see BUG-10) — the health check does not exercise a real embedding call, so it gave false confidence.

**Root cause:** Dependency drift — something installed `torch==2.14.0` after the pinned `torch==2.12.1+cu130`/`torchvision==0.27.1+cu130` pair was set up, breaking the compiled-extension ABI between them.

**Fix applied (with explicit user approval, no app code touched):**
```
pip install torch==2.12.1+cu130 torchvision==0.27.1+cu130 --extra-index-url https://download.pytorch.org/whl/cu130
```
Verified post-fix: `sentence_transformers` imports cleanly, `BAAI/bge-m3` loads on CUDA at startup, all subsequent chat/search/upload calls returned 200.

**Recommendation:** Pin `torch`/`torchvision` with `==` (already done) AND add a CI/pre-deploy check that actually calls `SentenceTransformer(...).encode(["test"])` once, not just `pip check`, so a future drift is caught before it reaches a running server. Also fix BUG-10 (health check) so `/health` can't report a false "ok" for embeddings.

### BUG-02 — [FIXED] `GET/POST /draft-history` crashes 500 for every real draft (100% reproducible)
**Severity:** Critical | **Area:** Drafting / Draft history | **Explicitly named in the QA scope**

**Evidence:** `qa-50q-full-20260924/responses/T27b_draft_history_user_a.json`:
```json
{"error": {"code": "internal_error", "message": "An unexpected error occurred.", "details": {}}}
```
Server traceback (`backend_qa_50q_retest_20260924.log`):
```
File "app/drafting/engine.py", line 839, in history
    created_at=record["created_at"].isoformat(),
AttributeError: 'str' object has no attribute 'isoformat'. Did you mean: 'format'?
```

**Root cause (confirmed by code reading, `app/repositories/drafts.py` + `app/repositories/postgres_json.py`):** With `POSTGRESQL_ENABLED=true` (the current `.env`, i.e. the default configuration), both `list_for_session()` and `list_for_user()` read drafts via `load_payload(row["payload"])`, i.e. `json.loads()` on a JSONB text column. `dump_payload()` serializes `datetime` → ISO string on write (`_json_default`); `load_payload()` never converts it back on read. `engine.py:839` then unconditionally calls `.isoformat()` on that string. **This will crash for every single draft, every time, for both `session_id`- and `user_id`-scoped history**, because both code paths share the same `load_payload` round-trip. It is not user- or data-specific.

**Impact:** `/draft-history` is completely non-functional whenever Postgres is enabled — which it is by default. A user can trigger, fill, edit, translate, and export a draft perfectly (§ drafting tests below all pass), but can never list their own past drafts.

**Fix (for the dev to apply, not applied here):** In `app/drafting/engine.py::history()`, either parse `created_at` with `datetime.fromisoformat(record["created_at"])` before calling `.isoformat()`, or just pass the already-ISO string straight through to `DraftSummary.created_at` without re-calling `.isoformat()`.

### BUG-03 — [FIXED] RAG answers cite specific statute sections that are **not present** in the returned `sources`, without flagging as unverified
**Severity:** Critical | **Area:** Chat / citation accuracy — directly targets "citations ki validity" requirement

**Test:** T46 (XSS probe, incidentally doubled as a citation-accuracy probe) — question: *"&lt;script&gt;alert('xss')&lt;/script&gt; what is the punishment for theft?"*

**Evidence:** `qa-50q-full-20260924/responses/T46_xss_probe.json` — response has `no_verified_context: false`, `general_knowledge_used: false` (i.e. the system asserts this is a **verified, KB-grounded** answer), confidence `0.52`, and states:

> "Under the Bharatiya Nyaya Sanhita, the punishment for theft is governed by **Section 303(2)**. Generally, this offence is punishable by rigorous imprisonment for a term that must be at least one year but may extend up to five years..."

But the `sources` array actually returned is:
```
THE BOMBAY HABITUAL OFFENDERS ACT — Section 20
The Bharatiya Nagarik Suraksha Sanhita — Section 229   (procedural code, not BNS)
The Bharatiya Nagarik Suraksha Sanhita — Section 395   (procedural code, not BNS)
```
**None of the 6 returned sources is the Bharatiya Nyaya Sanhita (the substantive code the answer names), and none is Section 303.** The specific section number quoted to the user is not backed by anything in the citation list shown alongside it — worse than an honest "no verified context" refusal (which the system correctly produces elsewhere, see T06/T08/T12/T13), because here it dresses up an unverified claim as verified.

**Fact-check:** The underlying legal claim (BNS §303(2), theft, 1–5 years RI, the sub-Rs.5000-return exception) is substantively accurate as *general knowledge*, but the system is not entitled to present it as KB-verified when its own retrieval didn't find it.

**Why this matters most:** this is exactly the failure mode grounding/citation systems exist to prevent, and it is the one the user explicitly asked to fact-check for ("unsupported answer ko PASS mat karo"). **Marked FAIL.**

**Recommendation:** Add a hard post-generation check: any statute/section number named in the answer text must appear in the `sources`/`retrieved_sections` list, or the response must be forced into the `no_verified_context`/general-knowledge path with the disclaimer already used elsewhere in this same app (see T06/T08/T13 — that code path exists and works correctly, it just wasn't applied here).

### BUG-04 — Knowledge base is missing the Bharatiya Nyaya Sanhita (BNS) as a complete bare act
**Severity:** Critical | **Area:** KB content coverage

**Evidence (direct MongoDB query against the live KB, read-only):**
```
db.embeddings_metadata.count_documents({"metadata.act_name": {"$regex": "Nyaya"}})  → 16 chunks total
```
All 16 are fragments (UP ordinance cross-references, an "Investigating Officer Handbook" mentioning procedural sections like 173/176/210) — **zero chunks** are a complete, section-by-section bare-act text of the BNS. Compare: the **procedural** code (Bharatiya Nagarik Suraksha Sanhita, BNSS) is well indexed — `Bharatiya_Nagarik_Suraksha_Sanhita_2023_Complete_Act.pdf` and `BNSS_2023_Official_Gazette.pdf` both present with hundreds of chunks. A direct `/search` for `"murder punishment Bharatiya Nyaya Sanhita section 103"` returned only noise (Orissa Co-operative Societies Act, Maharashtra Maritime Board Act, top score 0.016).

**Impact:** The BNS is India's core **substantive** criminal code — murder (§103), culpable homicide, theft (§303), sexual offences, hurt, dowry death, etc. Any citizen asking "what is the punishment for X crime" in the most natural way possible gets an honest-but-unverified general-knowledge answer (T06, and indirectly contributes to T46's fabricated-citation failure, since retrieval had nothing real to return). This is a foundational content gap for a criminal-law-facing "Indian Legal AI Assistant."

**Recommendation:** Ingest the official BNS 2023 gazette/bare act (same pipeline already used for BNSS) as the top content-priority item — this is higher-impact than any of the other bugs found here.

## 2. High-severity bugs

### BUG-05 — Drafting-intent detection fails for Hindi and English "narrative + trigger phrase" messages
**Severity:** High | **Area:** Conversational drafting engine

**Evidence:**
- T19 — Hindi: *"पुलिस शिकायत दर्ज करनी है, मेरा मोबाइल फोन चोरी हो गया"* (contains the literal configured trigger phrase "पुलिस शिकायत") → `draft: null`, `conversation_intent: "General Legal Information"`. Answered as an FYI-only answer instead of starting the `police_complaint` template.
- T20 — English: *"I need to file an RTI application about a delayed passport"* → same failure, `conversation_intent: "General Legal Information"`.
- T22 — a detailed field-filling follow-up sent into an (intended) already-drafting session also got reclassified as `"Legal Advice"` with `draft: null`, ignoring the drafting context entirely.
- **Contrast:** T21 — Hinglish, terse: *"cheque bounce ho gaya hai, notice draft karna hai"* → correctly entered `stage: "collecting"` for `cheque_bounce_notice`.

**Pattern:** short, drafting-verb-heavy phrasing works; a message that also narrates first-person facts ("my phone was stolen", "about a delayed passport") gets reclassified by the LLM intent step as an advice-seeking question, overriding the keyword trigger-phrase match. Since real users describing their problem is the normal, expected way to start a complaint/RTI/notice (the app's own trigger-phrase examples in `police_complaint.yaml` are literally phrased this way), this materially undermines the "detects drafting intent automatically... in English, Hindi, Hinglish" feature the README advertises as the app's core differentiator.

**Recommendation:** When a configured `trigger_phrase` literally matches (substring or fuzzy) the incoming message, that should short-circuit or at minimum heavily weight against the general LLM intent classifier, rather than being silently overridable by it.

### BUG-06 — RAG retrieval has degraded recall for Hindi/Hinglish queries even when the target content exists in the KB
**Severity:** High | **Area:** Chat / RAG retrieval quality

**Evidence:**
- T08 — Hinglish: *"dahej lene ki kanooni saza kya hai India mein?"* (what is the legal punishment for taking dowry) → `no sources`, `general_knowledge_used: true`. But `DOWRY_PROHIBITION_1961_Official.pdf` **is** indexed (12 chunks, confirmed via direct Mongo query, including Section 3 — the punishment section itself).
- T10 — Hinglish: *"RTI Act 2005 ke section 6 mein kya provision hai application dene ke liye?"* → `no_verified_context: true`. The RTI Act has **121 chunks** indexed, yet retrieval surfaced nothing usable.
- By contrast, T07 (English, NI Act §138) and T09/T22 (Hinglish, but phrased as a full narrative about an FIR) retrieved correctly with accurate section-level citations.

**Impact:** Users asking in Hindi/Hinglish — presumably the majority of this app's target audience, given it's built for a multilingual Indian audience — get "sorry, nothing verified" or ungrounded answers noticeably more often than English users, for content that is demonstrably present in the KB.

**Recommendation:** Investigate the query-rewriting/embedding step specifically for short Hindi/Hinglish conceptual queries (as opposed to English or long narrative Hinglish) — possibly a query-expansion or reranking threshold issue rather than a missing-content issue, since the content is confirmed present.

### BUG-07 — [FIXED] `/draft-history` has no ownership check for session-scoped queries (latent, currently masked by BUG-02)
**Severity:** High | **Area:** Access control

**Evidence (code reading, `app/api/drafting.py::draft_history`):**
```python
effective_request = request.model_copy(update={"user_id": user_id or None})
drafts = await LegalDraftEngine().history(effective_request)
```
and in `engine.py::history()`:
```python
if request.session_id:
    records = await self.drafts.list_for_session(request.session_id, request.limit)
elif request.user_id: ...
```
Because `session_id` branches **before** any ownership comparison, any caller who supplies someone else's `session_id` (JWT identity is irrelevant here) gets routed straight to that session's drafts with **no ownership check at all** — unlike `/history` and `/session`, which do enforce ownership (confirmed: T30 cross-user probe against `/history` correctly returned `403 "This session belongs to a different account."`).

**Live test:** User B's JWT + User A's `session_draft3` → `500` (currently masked by BUG-02's crash before any ownership logic would even matter) rather than a clean `403`. Once BUG-02 is fixed, this becomes a live cross-user data leak: any authenticated user who learns/guesses another user's `session_id` can read that user's full draft history and content.

**Recommendation:** Add the same ownership check used by `/history`/`/session` to the session-scoped branch of `LegalDraftEngine.history()` before BUG-02 is fixed, so the fix for one doesn't silently expose the other.

### BUG-08 — Field extraction inconsistently requires "label is X" / "label: X" phrasing for address fields
**Severity:** High | **Area:** Drafting field extraction

**Evidence:** Filling a cheque-bounce draft with a single natural comma-separated message —
> "...address 22 Karve Road Pune, mobile 9123456780, drawee bank name HDFC Bank, cheque amount Rs 75000... respondent address 5 FC Road Pune, respondent name Suresh Traders"

— correctly extracted mobile, bank name, amount, cheque date/number, dishonour date/reason, place, and respondent name, but **left `applicant_address` and `respondent_address` in `missing_fields`** (`T22b_draft3_fill_fields.json`). A retry with explicit connector words — *"applicant address **is** 22 Karve Road Pune 411004. respondent address **is** 5 FC Road Pune 411005."* — was captured immediately and the draft completed (`T22d_draft3_fill_with_is_phrasing.json`).

**Impact:** Numeric/pattern-shaped fields (phone, amount, date, cheque number) tolerate natural comma-separated phrasing; free-text address fields apparently need an explicit "is"/colon connector. This silently blocks draft completion for a very plausible, natural way of describing an address, forcing an extra back-and-forth turn the user shouldn't need.

**Recommendation:** Extend the `"label: value"` / `"label is X"` regex in `app/drafting/field_extraction.py` to also match `"label <value starting with a digit or place-name>,"` (the same shape already handled for phone/amount/date), or route addresses through the LLM structured-extraction pass unconditionally rather than relying on the regex pass alone.

## 3. Medium-severity bugs

### BUG-09 — `/entities` fails to extract a person's name even for the documented "My name is X" pattern
**Severity:** Medium | **Area:** Entity extraction

**Evidence:** `T39_entities_extract.json` — input: *"My name is Rohan Sharma, contact me at rohan@example.test or 9876543210, incident happened on 10 September 2026, amount involved Rs. 50000."* Phone, email, amount, and date were all extracted correctly with 0.8+ confidence; **no `name` entity was returned at all**, despite the README explicitly documenting `"my name is X"` as a supported extraction pattern.

**Recommendation:** Add a regression test for this exact documented pattern; the regex/heuristic extractor appears to have a gap here even though the capability is advertised.

### BUG-10 — `/health` reports `"embedding": "ok"` without exercising a real embedding call
**Severity:** Medium | **Area:** Observability

**Evidence:** During the entire pre-fix window (BUG-01), every `/chat`/`/search`/`/upload` call failed with the embedding `ModuleNotFoundError`, yet `curl /health` consistently reported `"embedding": "ok"`. A health check that can't detect its own core dependency is broken should not report healthy.

**Recommendation:** Have the embedding health check actually call `embed_batch(["healthcheck"])` (cached/cheap) rather than a superficial check (e.g. "is the config set"), or a monitoring/alerting system built on top of `/health` will miss real outages exactly like the one found here.

### BUG-11 — `/health` transiently reports `redis: "unavailable"` immediately after a cold start
**Severity:** Low | **Area:** Observability

## 6. Wrong-answer root causes (summary)

1. **Content gap, not a model failure** (T06, contributes to T46): BNS bare act not ingested (BUG-04). The system's own safety net (honest "unverified" disclaimer) worked correctly here — T06 is PARTIAL, not FAIL, because it didn't lie.
2. **Retrieval recall gap for Hindi/Hinglish** (T08, T10): content exists in KB but wasn't surfaced (BUG-06) — likely an embedding/query-rewrite weakness specific to short Devanagari-script or conceptual (non-narrative) Hindi/Hinglish queries, since long narrative Hinglish (T09, T22) and English (T07) retrieved correctly.
3. **Citation/grounding-check gap** (T46): the LLM was allowed to name a specific section number that its own retrieval step didn't return, and the response wasn't routed through the same "unverified" disclaimer path used successfully elsewhere in this same codebase (BUG-03). This is a missing post-generation guardrail, not a missing feature — the guardrail clearly exists (T06/T08/T12/T13 all used it correctly) and just wasn't applied consistently.
4. **Intent-classifier override of keyword triggers** (T19, T20, T22): the LLM-based conversational-intent step outranks an exact trigger-phrase match when both a drafting trigger phrase and a first-person narrative are present in the same message (BUG-05).
5. **Environment drift, not code** (pre-fix T06–T23, T31, T32, T45, T46): `torch`/`torchvision` version mismatch (BUG-01, fixed this session).

### BUG-03 fix — `app/rag/citation.py`

`LegalCitationEngine.validate_grounding()` previously only checked that *some* non-empty citations existed — never that the specific section number the generated prose leans on is actually among them. Added:

```python
_SECTION_MENTION_RE = re.compile(r"(?:Section|Sec\.?|धारा|U/S)\s*[:\-]?\s*(\d+[A-Za-z]?)", re.IGNORECASE)

def _mentioned_sections(answer: str) -> set[str]:
    return {match.group(1) for match in _SECTION_MENTION_RE.finditer(answer)}
```
and, inside `validate_grounding`:
```python
mentioned_sections = _mentioned_sections(answer)
cited_sections = {citation.section for citation in citations if citation.section}
if mentioned_sections and cited_sections and mentioned_sections.isdisjoint(cited_sections):
    return False, "The answer cites a section number that does not match any retrieved/verified source."
```
Deliberately conservative — it only fails when **none** of the section numbers named in the answer overlap with what was actually retrieved, so an answer that legitimately discusses a couple of background sections alongside its main citation isn't penalised. Verified against three cases before touching the live server: the exact T46 fabrication scenario (now correctly returns `False`), the T07 correctly-grounded scenario (still returns `True`), and an answer with no section numbers at all (still returns `True`, unaffected).
